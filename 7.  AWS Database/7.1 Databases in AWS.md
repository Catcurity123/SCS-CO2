#### A. Databases on EC2
(+) Database within the webserver and application tier or database in a different Instance.
![[Pasted image 20250807194909.png]]
(+) This is generally a bad approach, but there are some reason we might need to do it.
(+) `Access to DB Instance OS`: requirement from client or company to have direct access to OS. For example, advanced DB Option tuning (DBROOT), but AWS have many option for DB tuning without needing DBROOT.
(+) `Niche use case when DB or DB version AWS does not provide`: Where specific OS/DB combination AWS doesnt provide.

###### But we shouldn't really
(+) `Admin overhead`: maning EC2 and DBhost patch.
(+) `Backup/DR Management`: DB on EC2 will need additional backup management
(+) `Performance` AWS invest time into optimisaztion and features for its managed database service.
==> These happens because `EC2 is single AZ`.

#### B. Relational Database Service (RDS)
(+) Database-as-a-service (DBaaS) ==> DatabaseServer-as-a-service
(+) Managed database instance with multiple engines `MySQL, MariaDB, PostgreSQL, Oracle, Microsoft SQL Server` and `Amazon Aurora`

###### B1. RDS Architecture
(+) `RDS Database Instance`: where we use Database CNAME to access RDS instance. RDS behind the scene is attached to an EBS Storage in the same AZ.
==> Meaning EBS's type (io1, gp2, magnetic-hdd) should be taken into consideration for database usage.
==> Billed for allocated GB/m
