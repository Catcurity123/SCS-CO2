#### A. Databases on EC2
(+) Database within the webserver and application tier or database in a different Instance.
![[Pasted image 20250807194909.png]]
(+) This is generally a bad approach, but there are some reason we might need to do it.
(+) `Access to DB Instance OS`: requirement from client or company to have direct access to OS. For example, advanced DB Option tuning (DBROOT), but AWS have many option for DB tuning without needing DBROOT.
(+) `Niche use case when DB or DB version AWS does not provide`: Where specific OS/DB combination AWS doesnt provide.

###### But we shouldn't really
(+) `Admin overhead`: maning EC2 and DBhost patch.
(+) `Backup/DR Management`: DB on EC2 will need additional backup management
(+) `Performance` AWS invest time into optimisaztion and features for its managed database service.
==> These happens because `EC2 is single AZ`.

#### B. Relational Database Service (RDS)
(+) Database-as-a-service (DBaaS) ==> DatabaseServer-as-a-service
(+) Managed database instance with multiple engines `MySQL, MariaDB, PostgreSQL, Oracle, Microsoft SQL Server` and `Amazon Aurora`

###### B1. RDS Architecture
(+) `RDS` runs in a VPC inside a subnet either public or private, it can be accessed within a VPC or any connected private network (VPN, Direct Connect). `RDS` can also be configured with public addressing allowing access from the public internet.
(+) `RDS` instance can have more than 1 databases, behind the scene `RDS` has a dedicated storage(EBS) per instance.
(+) `RDS` can be `replicated synchronously` to a standby instance or `replicated asynchroniously` to a read-only replica.
(+) `RDS` backups can be performed by taking a snapshot and store on S3/

![[Pasted image 20260227151944.png]]

###### B2. RDS Cost Architecture
(+) Cost #1 - instance size and type: the bigger the more feature-rich instance, the greater the cost.
(+) Cost #2 - Multi AZ or not: since multi-az means more than 1 instance
(+) Cost #3 - Storage type & amount: depend on dedicated storage type (EBS)
(+) Cost #4 - Data transferred: data transferred out of region cost money
(+) Cost #5 - Backups & Snapshots
(+) Cost #6 - Licensing

###### B3. RDS Multi AZ Architecture 
###### Old Architecture - Multi AZ Instance
![[Pasted image 20260227153829.png]]
(+) Data is written to Primary and replicated to StandBy using Synchronous
(+) Not free tier meaning extra cost
(+) One StandBy replica Only, which can be used for reads or write
(+) 60 - 120 seconds failover when Primary DB fails, as the access to DB is using CName, and when the `Primary DB fails the DB CName has to be written to StandBy's CNAM` which is a DNS change which may take 60 - 120 seconds.
(+) Can only be applied for same region only, different AZs in the same region
(+) Backups can be taken from StandBy to improve performance.

###### New Architecture - Multi AZ Cluster Architecture
![[Pasted image 20260227154535.png]]
(+) This architecture consists of 1 Writer and 2 Readers DB Instances (different AZs), which is much faster read, faster writes as it is writing to local storage
(+) Readers can be used for reads, allowing read scaling
(+) Replication is via transaction logs, which is more efficient, and the failover is faster - 35s + transaction log apply
(+) Entry's writes are `committed` when 1 reader has confirmed the synchronization.
(+) Access to `RDS` in this architecture can be through `Cluster Endpoint`, `Reader Endpoint`, or `Instance Endpoint`

###### B4. RDS Backups, Snapshots and Restore
(+) `RDS` backups happens through 2 methods `Manual Snapshot` and `Automated Backups`
(+) `Snapshot`'s first snap is full size of consumed data, then onward, it will only be `incremental`
(+) `Automated backups` are snapshots that happen everyday, if we only have one `RDS` in AZ, then make sure it happens during `low-usage time` so that limited downtime occurs. If we are in multi-AZ architecture then the snapshot will happen on the StandBy or Read-Replica. It has a 0 -> 35 day retention for snapshots and 5 minutes for transaction logs.

###### Restore
(+) Will create a new RDS instance, meaning it will be a new address and we need to reconfigure the application.
(+) Snapshot is `single point in time`, meaning RPO (recovery point objective) will be affected as the when the disaster happens we can only restore the data from the `single point in time` up to the disaster, 
==> Although we have a 5 mins transaction log stored, the backup is restored and transaction logs are `replayed` to bring DB to desired point in time (`minimizing RPO`)
(+) Restore is not fast either, so it will also affect our RTO (recover time objective)

###### B5. RDS Read Replicas
(+) `5x` direct read-replicas per DB instance, each provide an additional instance of read performance.
(+) Read-replicas can have read-replicas, but lags starts to be a problem.
(+) Global performance improvement
==> RPO/RTO improvement
(+) Snapshots and Backups improve RPO since the more frequent the snapshots is the less data gonna be lost. `RPO is about how much data is loss`
(+) But it does not help with RTO, since although data is not loss the time it takes for snapshots to be restored is long. `RTO is about how long does it take to recover from disaster`
(+) Read-replica offer near 0 `RPO` since data is replicated asynchronously. RR can be promoted to be primary quickly so it will improve `low RTO`
==> This should only be used for disaster (meaning the primary database is down) and should not be used for corrupted data (since with 0 RPO the corrupted data will also be restored)
==> RR should remain to be read only until promoted, and this is a way to achieve global availability, global resilience

###### B6. RDS Custom
(+) RDS is a `fully managed` - OS/Engine access is limited. Comparing to DB on EC2 which is self managed ==> But has overhead
(+) Currently, RDS custom works or MS SQL and Oracle, which we can connect to using SSH, RDP, Session Manager
