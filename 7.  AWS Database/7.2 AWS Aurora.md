#### A. Aurora Key Differences
(+) Aurora is **not simply MySQL/PostgreSQL running on better hardware**. AWS forked the MySQL InnoDB and PostgreSQL engines and re-engineered how they read/write data to disk — specifically the `redo log` layer

(+) The core innovation: **"the log is the database."** Instead of writing full 16 KB data pages over the network (like traditional databases), Aurora only ships **redo log records** to the storage layer. The storage nodes reconstruct pages from those logs

==> This dramatically reduces network I/O

(+) Aurora still uses the **RDS control plane** for management (provisioning, monitoring, patching), but the data path is completely redesigned. The compute layer (writer + readers) runs on **AWS-managed EC2 instances**, same as RDS. You pick instance classes (e.g., `db.r6g.2xlarge`) just like RDS

(+) `Writer instance`: only one per cluster. Handles all write operations. If you need more write throughput, you must shard at the application level

(+) `Reader instances`: up to **15 read replicas** per cluster. Because they share the same storage, adding a replica doesn't mean copying terabytes of data — it just spins up a new compute node that points at the shared volume

###### A1. Write Path
(+) There is a single writer as a compute node, it will parse the SQL, apply transactions and then generate redo logs. Then it will send the redo logs to 6 storage nodes across 3 AZs
(+) A write is acknowledged only after 4 out of 6 nodes confirm persistence
==> Aurora can still write even if an entire AZ fails (meaning we lost 2 out of 6 still have 4 to confirm), assuming the the AZ that stores writer does not fail. This is called a `Quorum` - the minimum number of nodes that must agree for an operation to succeed.

###### A2. Read Path
(+) Reads do **not** use quorum under normal conditions — they're served from a **single, up-to-date storage node** to keep latency low

(+) The read quorum (3/6) is only used during **failure recovery** to identify the most recent consistent version of data

###### A3. Recovery Path
(+) Due to the architecture of Aurora, all compute instances share the same value, meaning in case of failover, the promotion of read to write is just a change of role, no data copy is needed

(-) In standard RDS, the failover works differently, each instance has their own storage volume, failover means changing the primary to standby and change the storage in primary to storage in standby

#### B. Aurora Storage Architecture
(+) `Cluster volume is a virtual distributed SSD` storage system: where all compute node share and they are fully decoupled.
(+) Aurora storage is `automatically elastic`, the storage start at 10GB and grow in 10GB increment. Up to 128TB. No need for manual provision.
(+) Aurora uses log-structured writes, where instead of sending the who page of database like traditional database, the write compute instance will send the command `INSERT...` as redo log to the storage node and in the storage node, the storage itself will rebuild the page.
(+) As a managed service, Aurora automatically self-heal when issue occur

###### Connection to Aurora is through endpoints:
(+) `Cluster endpoint`: The **cluster endpoint** is a **DNS address that always points to the current writer instance**. If failover happens it will switch to the DNS of the new writer. `Insert, Update, Delete` will go to this endpoint.
(+) `Reader endpoint`: The **reader endpoint** is another DNS address that **load balances across all reader instances**. `SELECT queries` will go to this endpoint

#### C. Aurora costs
(+) No free tier
(+) Compute - hourly charge, per second, 10 minutes minimum
(+) Storage - GB-month consumed, IO cost per request.
(+) 100% DB Size in backups are included
(+) Backups in Aurora work in the same way as RDS, but restore will create a `new cluster`
(+) We only `pay for the storage used` in Aurora, and the storage `does not shrink automatically` after being used, it will need to `OPTIMIZE TABLE` to do logical dump and restore.

#### D. Aurora Restore, Clone & Backtrack
(+) In Aurora, there are 3 different ways to recover or duplicate data:

(1) `Aurora Restore`: Restore creates a new Aurora cluster from a backup or snapshot. This is an automated backup similar to RDS (snapshot stored on S3) that provides Point In Time Recovery (PITR), useful for disaster recovery.

(2) `Aurora Clone`: Cloning creates a new Aurora cluster that shares the same underlying storage pages. This is usually use to clone db to another test db.

(3) `Aurora Backtrack`: Backtrack rewinds the entire database cluster to a previous point in time without restoring from backup. It works by **replaying or undoing redo logs in the storage layer**. Backtrack window is `1 hour to 72 hours`

#### E. Aurora Serverless
(+) Scalable using `Aurora Capacity Unit (ACU)`
(+) Aurora Serverless cluster has a Min and Max ACU, which can adjust based on load, and can go to 0 and be paused/
(+) Same resilience as Aurora Provisioned
