####  EC2 Overview
(+) EC2 instances are `virtual machines` (OS + Resource), EC2 Instance run EC2 hosts.
(+) Hosts can be `shared hosts` or `dedicated hosts`. 
(+) EC2 is `AZ resilient` as the Host runs in a single AZ, so host fails means instances falls.

#### A. EC2 Architecture
(+) EC2 host has local hardware such as CPU and memory and local storage called `instance store`, if `instances` move to different host this storage will be lost.
(+) When an `instance` is provisioned into a `subnet` within a `vpc`, a primary elastic interface is provisioned in that subnet that maps to the physical hardware on the EC2 host.
(+) EC2 can connect to remote storage called Elastic Block Store or EBS. EBS allows us to allocate volume which can be then allocated to EC2.
(+) Remember that EC2, Subnets, Network, and persistent stoarage are in an `Availability Zone`.
(+) Instances can have multiple interfaces even in different subnets, as long as they are in the same AZ.

#### B. EC2 Instance Type, Pricing Model, Tenancy, Fleet, Placement Group

###### 1. EC2 Types
(+) EC2 Instance Type affects raw CPU, Memory, Local Storage Capacity & Type.
(+) `Resource Ratios` and `Storage` and `Data` network `bandwidth`.
(+) System Architecture/ Vendor, and additional features and capabilities. There are:

(+) `General Purpose` - Default - Diverse workloads, equal resource ratio.
(+) `Compute Optimized` - Media Processing, HPC, Scientific Modelling, gaming, ML.
(+) `Memory Optimized` - Processing large in-memory datasets, sone database workloads.
(+) `Accelerated Computing` - Hardware GPU, field programmable gate arrays (FPGAs).
(+) `Storage Optimized` - Sequential and random IO - sacle-out transactional databases, data warehousing, Elasticsearch, analytic workloads.

|Type|Designed For|Key Back-End Distinction|When to Use|
|---|---|---|---|
|General Purpose|Versatile, balanced|Even CPU:RAM:network; no extras|Web apps, test/dev, generic business apps|
|Compute Optimized|CPU-intensive throughput|Fast CPUs, high clock, large cache|Media processing, HPC, analytics, ML inference|
|Memory Optimized|Large, fast RAM|High RAM:CPU, many RAM slots|In-memory DBs, fast analytics, SAP, genomics|
|Accelerated Comp.|Parallel HW acceleration|Real HW GPUs/FPGA, custom chips|Deep learning, rendering, scientific custom workloads|
|Storage Optimized|Fast, local SSD (NVMe)|Many NVMe drives per host|NoSQL, big data, warehousing, log/analytics ingestion|

###### 1.1 Technical differences:
(+) `General Purpose`: Equal proportions of CPU, memory, and network resources (e.g., M, T, A series).
(+) `Compute Optimized`: More vCPUs per GB RAM than general purpose (e.g., C series), Larger CPU caches for faster computation. Underlying host hardware is tuned for maximum compute throughput and scalable parallelism.
(+) `Memory Optimized`: Memory-to-CPU ratio is much higher (e.g., R, X, Z series). Underlying hosts are loaded with high-capacity RAM modules, SODIMM in dense configurations.
(+) `Accelerated Computing`:  Attachments like NVIDIA GPUs (P, G, DL series), FPGA (F series), custom AWS Inferentia chips. Physical servers are equipped with PCIe or NVLink-connected accelerators alongside CPUs.
(+) `Storage Optimized`: Multiple high-IOPS NVMe SSDs (I3, I4, D series), sometimes many TBs with RAIDed disk configs. Hosts physically packed with fast NVMe drives, hardware RAID, with cooling and power for constant heavy I/O.

###### 1.2 Example of use cases:
###### General Purpose:
(+) `Web Application hosting:` Mid size website that handles moderate traffic with balanced compute, memory, and networking needs,
(+) `Development and Testing Environment:` Software development teams creating isolated environments for each developer or feature branch for testing

###### Compute Optimized:
(+) `Machine Learning Inteference`: Real ime image recognition or natural language processing that require high CPU performance for model inference but dont need extensive GPU acceleration.
(+) `Scientific Computing and Modeling:` Climate modeling, genomic analysis or financial risk calculation that involve complex mathematical computation requiring high-performance processors.

###### Memory Optimized:
(+) `In-Memory Database:` Redis cluster or SAP HANA implementation that store large datasets entirely in RAM for ultra-fast query performance
(+) `Real-time Big data analytic:` Apache Spark applications processing terabytes of streaming data from IoT sensors or financial data requiring large memory buffers

###### Accelerated Computing:
(+) `Deep Learning Model Training:` Training large neural networks for computer vision or natural language processing using GPU parallelization to reduce training time from weeks to days
(+) `3D Rendering and Video Processing:` Movie studios rendering CGI sequences or real-time video transcoding for streaming platforms requiring GPU acceleration

###### Storage Optimized:
(+) `Distributed NoSQL Databases` MongoDB or Cassandra clusters requiring high-throughput, low-latency access to large datasets stored locally on NVMe SSDs
(+) `Data Warehousing and Analytics` Elasticsearch clusters or data lakes processing massive log files and requiring sequential read/write operations at high IOPS

6. **Question:** When would you choose a Memory Optimized instance over a Storage Optimized instance for a database workload?  
==> Choose Memory Optimized when the database working set fits in RAM and you need fast query response times. Choose Storage Optimized when dealing with very large datasets that require high-throughput disk I/O operations.

7. **Question:** What's the key difference between General Purpose and Compute Optimized instances for a web application?

==> Use Accelerated Computing for training deep neural networks or complex model inference requiring parallel processing. Use Compute Optimized for simpler ML algorithms, data preprocessing, or feature engineering that primarily need CPU power.

###### 3. Instance Pricing Models
(+) `On-Demand Instances:` Instances have an hourly rate, billed in `seconds` (60s minimum) or `Hourly` , no long-term commitments or upfront payments. Good for new or uncertain application requirements or `short-term`, `spiky`, `unpredictable` workloads which `can't tolerate any disruption`.

(+) `Spot Instance`: Spot pricing offers up to 90% off vs On-Demand. A spot price is set by EC2 - based on `spare capacity`. You can sprcify a `maximum price`, if spot price goes above yours `instance terminated`, therefore, it is only used for apps which `can tolerate failure`.

(+) `Reserved Instances`: up to 75% off vs On-demand - `for a commitment`. Buy 1 or 3 years in advance (all upfront, partial upfront, no upfront). `Reserved in region`, or AZ with capacity reservation. Good for `Known stady state usage`, low cost for apps which `cant handle disruption`.

(+) `Saving Plan`: Flexible pricing with commitment to a set spend over time

###### 4.Tenancy
###### 4.1 Dedicated Instances:
(+) `Dedicated Instances`: Physical isolation at the host hardware level from instances belonging to other customers; pay per instance.
(+) `Regulatory Compliance Requirements`: Organizations in healthcare, finance, or government sectors that require physical isolation from other customers' workloads due to regulatory mandates or security policies. These instances provide hardware-level isolation while remaining within the AWS shared responsibility model
![[Pasted image 20250805220905.png]]

###### 4.2 Dedicated Host:
(+) `Dedicated Host`: Physical server dedicated for your use; Socket/core visibility, host affinity; pay per host; workloads with server-bound software licenses.
(+) `Bring Your Own License (BYOL) Scenarios`: Software licensing models that are bound to sockets, cores, or physical servers, such as Windows Server, SQL Server, Oracle, or SUSE Linux Enterprise Server. Dedicated Hosts provide socket and core visibility required for per-socket or per-core licensing.
![[Pasted image 20250805220525.png]]

###### 5. EC2 Fleet (scaling)
###### 5.1 Spot Fleet:
(+) `Fault-Tolerant Distributed Applications`: Applications that can distribute workload across multiple instances and handle instance terminations gracefully. Spot Fleet automatically manages the collection of Spot instances, maintaining target capacity while optimizing for lowest costs across multiple instance types and availability zones.

###### 5.2 EC2 Fleet:
(+) `Mixed Workload Optimization`: Applications requiring a combination of guaranteed capacity (On-Demand/Reserved) for baseline performance and cost-optimized capacity (Spot) for burst requirements. EC2 Fleet enables single API management of diverse instance types and purchasing models.





###### 6. EC2 Placement Groups
Normally, when we start an instance, AWS choose which host to place the instance, this configuration allows us to choose the arrangement of instances.

(+) `Cluster`: pack instances close together inside an AZ. this enables workloads to achieve the low-latency network performance for tightly-coupled node-to-node communication like a HPC applications. Allow for 10Gbps p/stream.
![[Pasted image 20250805230113.png]]

(+) `Partition`: spreads instances across logical partitions so that instances do not share the underlying hardware. Each partition is located on a separate AWS Rack, and they can be in multiple AZs.  This is used by large distributed and replicated workloads, such as Cassandra, and Kafka.
![[Pasted image 20250805230355.png]]

(+) `Spread`: Strictly places a small group of instances across distinct underlying hardware to reduce correlated failures. As each instance is located on a separat AWS rack.
![[Pasted image 20250805230226.png]]

#### C. Scaling
###### C1. Vertical Scaling
(+) Each resize requires a reboot ==> `disruption`
(+) Larger instance often carry a `$ premium`
(+) There is an upper cap on performance ==> `instance size`
(+) `No application modification` required
(+) Works for all application - even `Monoliths`

###### C2. Horizontal Scaling
(+) Session between different instances can be a problem
(+) Requires application support or `off-host sessions`
(+) `No disruption` when scaling
(+) `No real limites` to scaling
(+) Often less expensive without instance premium

#### D. EC2 Optimization
###### 1. Enhance networking
(+) Without `SR-IOV`, the network card is not `virtualization aware`, meaning the host has to sit between NIC and ENI for networking tasks.
(+) Uses `SR-IOV` - NIC is virtualization aware, NIC does not need host to control which card is communicating at one time. The physical card will control the networking task without using Host's resource.
(+) No charge - available on most EC2 Types, with `Higher I/O, Lower Host CPU Usage` with more `Bandwidth`
(+) Higher packets-per-second (`PPS`), consistent lower `latency`.
![[Pasted image 20240201150510.png]]

###### 2. EBS Optimized
(+) `EBS` = block storage over the network.
(+) Historically network was `shared` .. `data` and `EBS`.
(+) EBS optimized means dedicated capacity for EBS.
(+) Most instances `support` and have `enabled by default`. Some support, but enabling costs extra.
