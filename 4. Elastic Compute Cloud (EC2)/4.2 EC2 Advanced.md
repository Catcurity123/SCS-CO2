###### A.2a : Nitro Cards for VPC networking
(+) VPC data-plane offload: ENI attachment, SG, flow logs, routing, limiters, DHCP, DNS
(+) VPC encryption: Authentication and transparent ete 256-bit encryption
(+) Elastic Network Adapter (ENA): Extendible host interface
(+) Elastic Fabric Adapter (EFA): ML and HPC UltraCluster, RDMA and GPU-RDMA, for low latency at scale and multi pathing (Scale Reliable Diagram)

###### A.2b Scale Reliable Diagram
(+) TCP only uses a single path at a time, where SRD provides foundation to use multiple path simultaneously. This is extremely valuable for distributed application and bulk synchronous applications.
(+) This allows ENA Express, which will offload TCP/UDP connection to different path using the Nitro Cards.

###### A.2c : Nitro Cards for Storage
(+) NVMe Controller: Standard drivers broadly available
(+) EBS data plane: encryption support, NVM to remote storage protocol

###### A.2d: Nitro Cards for Instance Storage
(+) In Traditional SSD design, NAND is where we write the bit into, it will need to be cleaned off before writing new bits. So a Flash Translation Layer (FTL) is needed to map logical to physical address and perform garbage collection
(+) Different SSD may have different FTL, so Nitro cards has a single FTL for all

###### A.2e: How is an instance launched
![[Pasted image 20250804220905.png]]
`(1)`: Your API hits EC2 control plan, and the control plan make the request to Nitro controller (controlling a server) asking it to allocate resource (in terms of computing like vCPU and RAM) for the particular request.
`(2)`: Nitro Controller talks to the Hypervisor (control the actual hardware) about the request
`(3)`: Nitro Hypervisor reserve the instance's resource
`(4)`: Then the control plane ask the nitro controller to attach fundamental devices (ENA, ENI, storage)
`(5)`: All those virtual cards for resources are then attach to Nitro Cards. No Hypervisor actions are in place. Hypervisor only allocate resources. And henceforth, connection between these virtual cards to physical cards is done without the help of the hypervisor.
`(6) + (7)`: Start the instance. Where the firmware looks at the boot volume, find the code to boot and boot it.

###### A.3 User data, Instance Metadata, and checks
###### User data
(+) User data is the bootstrap script provided at the launching phase of our EC2.

###### Instance Metadata
(+) EC2 Service provides data to Instances, which is accessible inside ALL instance. Access via `http://169.254.169.254/latest/meta-data`.
(+) Stored information about the `Environment, Networking, Authentication, User-Data` of the instance. It is `not authenticated or encrypted`.

###### Combining EC2 Metada and User data
(+) In the following simple bootstrap script, we use the `curl` command to save our EC2 metadata.
```

Bootstrap script for an Amazon Linux 2023 instance:

#!/bin/bash
yum update -y
yum install httpd -y
systemctl start httpd
systemctl enable httpd
cd /var/www/html
echo "<html><body><h1>My IP is" > index.html 
TOKEN=$(curl -s -X PUT "http://169.254.169.254/latest/api/token" -H "X-aws-ec2-metadata-token-ttl-seconds: 21600")
PUBLIC_IP=$(curl -s -H "X-aws-ec2-metadata-token: $TOKEN" http://169.254.169.254/latest/meta-data/public-ipv4)
echo "$PUBLIC_IP" >> index.html
echo "</h1></body></html>" >> index.html
```

#### . The component of a running EC2 Instance.

##### A. Physical host
(+) EC2 runs on servers in **AWS data center**, AWS data center host many **instances**, an EC2 instance is a virtual server and is managed by the **customer**.
(+) A selection of **instance types** come with varying combination of CPU, memory, storage and networking


##### B. Networking components.
(+) The main component of networking is the **Virtual Private Cloud (VPC)** which is our network infrastructure on AWS, which will have many **Availability Zones (AZ)**, within the AZ, we can create **Subnet**, either Private or Public.
(+) When we launch an EC2 instance in a VPC, the instance will be attached with a **Elastic Network Interfaces (ENIs)** which will allow us to communicate with other entities.


##### B. Storage
(+) Storage can be **persistent** or **ephimeral**. For persistent storage, we have **Elastic Block Store (EBS)**, which will grant us a block storage in an AZ, and attached to our EC2 over the network
(+) For ephimeral storage, we have **Instance Store**, which is a storage that is attched physically to the server (rather than through the network through ENI like EBS).
