#### A. Why Event-Driven?
(+) `Monolithic architecture` build together, fails together, scales together, bills together, and fails together.

(+) `Tiered Architecture` can scale independently, but it is ultimately very coupled, each tier connect directly to the endpoint of another tier. So it can scale horizontally.
==> However, each tier expect and requires each other to proceed and respond.

(+) `Queue-based decoupled Architecture` does not expect an immediate answer from different tier. The queue has decouple each tier, so they can work `asynchronously`. If there is a bottleneck at any tier, we can auto scale that particular tier depending on the queue length.

(+) `Microservice Architecture`: breaks an application into small, independent services, each responsible for a specific business capability.  
Each service runs its own process, owns its own data, and communicates with other services via lightweight APIs (e.g., HTTP/REST, gRPC, or messaging).

(+) `Event Driven Architecture`: No constant running or waiting, `Producer` generates events when something happens. Events are then delivered to `consumer` by `event router`. Then actions are taken and system returns to waiting.
