#### A. What is EBS
(+) `Block` storage - `raw` disk allocations (`volume`) - can be `encrypted` using `KMS`, instances see `block device` and create `file system` on this device (ext3/4, xfs)
(+) Storage is provisioned in `One AZ` (Resilient in that AZ).
(+) Attached to `one` EC2 instance (or other service) over storage network, it can be `detached` and `reattached`, not lifecycle linked to one instance, meaning it is `persistent`.
(+) Snapshop (backup) into S3. Create volume from snapshot (migrate `between AZs`)
(+) Different physical storage `types`, different `sizes`, different `performance profiles`
(+) billed based on `GB-month` (and in some cases `performance`)

###### A1. EBS Volume Types and General Purpose SSD
(+) `GP2` can be as small as 1GB or as large as 16TB.
(+) `IO Credit` is 16KB chunk of data, so if we transfer 160KB of data, it is 10 IO Credit, and 1 IOPS is 1 IO in 1 second
(+) `IO Credit Bucket` has a capacity of 5.4 million IO credit, fills at rate of `Baseline Performance`. The bucket is fills with minimum `100 IO Credit` per second `regardless of volume size`. Beyond 100 minimum, the bucket fills with `3 IO Credit per second, per GB of volume size` (baseline performance) and can burst up to 3,000 IOPS by depleting the bucket.
(+) All volumes get an initial 5.4 millions IO Credit, 30 Minutes @ 3,000 IOPS. Great for boots and initial workloads.
(+) Up to maximum for GP2 of 16,000 IO Credit per second, if the volumes is larger than 1,000 GB - baseline is above burst. Credit system isnt used and you always achieve baseline.
==> Great for boot volumes, low-latency, interactive apps, dev & test.

###### Example use case
1. **Database workloads** - Random access patterns with small block sizes
2. **OLTP applications** - Frequent small transactions
3. **Web servers** - Many concurrent small file requests
4. **File servers with many small files** - Document management systems

**Example**: An e-commerce database with 4KB transactions needs high IOPS:
- **Workload**: 10,000 transactions/second with 4KB each
- **IOPS requirement**: 10,000 IOPS
- **GP2 volume size needed**: 10,000 ÷ 3 = **3,334 GiB**
- **Actual throughput**: 10,000 IOPS × 4KB = 40 MiB/s (well below 250 MiB/s limit)

###### **Use Throughput for:**
1. **Big data analytics** - Sequential large block reads
2. **Video streaming** - Large sequential file access
3. **Backup and restore operations** - Large file transfers
4. **Data warehousing** - Large query result sets

**Example**: A data analytics workload processing large files:
- **Workload**: Reading 1MB blocks sequentially
- **Throughput requirement**: 200 MiB/s
- **IOPS calculation**: 200 MiB/s ÷ 1MB = 200 IOPS
- **GP2 volume size needed**: Only **334 GiB** (for 250 MiB/s capability)
- **Actual IOPS used**: ~200 IOPS (well below the 1,002 baseline)

###### **Scenario 1: Small Random I/O (IOPS-bound)**
`Application: MySQL database with 8KB random reads/writes IOPS needed: 5,000 GP2 volume required: 5,000 ÷ 3 = 1,667 GiB Actual throughput used: 5,000 × 8KB = 40 MiB/s Cost efficiency: Poor (paying for 1.6TB when only ~40GB might be needed) Recommendation: Consider GP3 for better cost efficiency`

###### **Scenario 2: Large Sequential I/O (Throughput-bound)**
`Application: Log processing with 256KB sequential reads Throughput needed: 200 MiB/s GP2 volume required: 334 GiB (minimum for 250 MiB/s) IOPS used: 200 MiB/s ÷ 256KB = 800 IOPS Cost efficiency: Good (volume size reasonable for storage needs)`

###### **Scenario 3: Mixed Workload**
`Application: Data warehouse with both small queries and large scans Peak IOPS needed: 2,000 (for small queries) Peak throughput needed: 150 MiB/s (for large scans) GP2 volume required: Max of (2,000÷3 = 667 GiB) or (334 GiB for throughput) Chosen size: 667 GiB Cost efficiency: Reasonable for mixed workloads`

###### A4. EBS Volume Types - Hard Disk Drive (HDD)-based
###### ST1 HDD Storage
(+) HDD is good for sequentially access data, not random access data. Good for data to be written and read sequentially. 
(+) 125GB -> 16 TB, Max 500 IOPS but with 1 MB of size meaning `500MB/s`. `40MB/s/TB for Base` and `250MB/s/TB for Burst`
(+) Frequent access, throughput-intensive, and sequential
==> Big data, data warehouse, log processing.

###### SC1 HDD Storage
(+) MAX 250 IOPS with size of 1MB, Max 250 MB/s.
(+) Lower cost HDD volume designed for less frequently access workloads

###### 4. EBS Performance
###### A Few definition
(+) `IOPS`: Input/Output operation per seconds, typically 256KB (#)
(+) `Throughput`: Read/write rate to storage (MB/s)
(+) `Latency`: Delay between request and completion (ms)
(+) `Capacity`: Volume of data that can be stored (GB)
(+) `Block size`: Size of each I/O (KB)

###### Counting IOPS
(+) Application use case can be random I/Os or sequential I/Os.

#### B. EBS Snapshots
(+) Snapshots are incremental volume copies to S3, as it is copied to S3, it is `region-resilence`.
(+) The first is a full copy of data on the volume not the full data limit of the storage.
(+) Future snaps are `incremental`, meaning the differnece between the current  data and the future data. For other backup system, using `incremental backup` presents a risk of if losing the incremental backup, the rest of the backup data from that point onward would also be lost. However, EBS's incremental backup can also be thought of as self-sufficient as losing an incremental backup would not affect the rest of the backup.
![[Pasted image 20240909161336.png]]

(+) Volumes can be created (restored) from snapshots, and can be copied to another region.
![[Pasted image 20240909161309.png]]

(+) New EBS volume = `full performance immediately`. Snaps `restore lazily` meaning that it will fetch the data gradually. But we can requested blocks are fetched immediately by forcing a read of all data.
(+) `Fast Snapshot Restore (FSR)` enables to restore immediately, up to 50 snaps per region.
(+) Snapshot consumption and billing are GB-per month but this is billed per `used data` not the `allocated data` meaning that if we used 10GB out of 40GB EBS and we create a snap for that EBS we will only be billed for 10GB. And in the future if we changed 4GB of that 10GB data, and create another snaps, we will only be charged for 4GB. Charged for `used data and changed data` not the `allocated data`.

#### C. EBS Encryption
(+) Data is stored in plaintext at rest without specification of encryption.
(+) EBS encryption can be via using AWS managed key `aws/ebs` or customer managed key.
(+) The key is used to create a `Data encryption key` `(DEK)`. This DEK is used to encrypt data stored on EBS
(+) The decyption key is stored in memory in the EC2 host that the EC2 is currently using EBS.
![[Pasted image 20250806233947.png]]
(+) Accounts can be set to encrypt by default - default KMS key
(+) Otherwise choose a KMS key to use
(+) Each volume uses 1 unique DEK
(+) Snapshots & future volumes use the same DEK
(+) Cant change a volume to not be encrypted
==> OS is not aware of the encryption so no performance loss

(+) This is referred to as `Envelop Encryption`, where the DEK is used to encryp and decrypt data. The `master key` is used to encryp/decrypt DEK whenever it is need.
